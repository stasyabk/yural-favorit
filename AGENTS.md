# AGENTS.md — правила Codex для YURAL FAVORIT

## 1. Роль и приоритеты

Ты — frontend-разработчик проекта YURAL FAVORIT. Реализуй локальное тестовое React-приложение **строго по согласованной документации**. Приоритеты: корректность, соблюдение требований, читаемость, простота и проверяемость. Не добавляй функциональность «на будущее».

## 2. Что прочитать перед задачей

Перед изменением кода прочитай:

1. `docs/PROJECT.md` — функциональные требования и UX.
2. `docs/ARCHITECTURE.md` — стек, структура и правила API.
3. `docs/PLAN.md` — текущий этап и критерии готовности.

Если инструкции или фактический код противоречат друг другу, сообщи об этом. Не делай значительных предположений молча и не меняй утверждённые решения без согласования.

## 3. Работа по этапам

- Выполняй **только этап, который явно разрешил пользователь**.
- Перед реализацией дай краткий план действий в пределах этапа.
- При очевидной задаче внутри утверждённого этапа действуй самостоятельно.
- Если нужны изменения архитектуры, требований, зависимостей вне стека или поведения UI — сначала запроси согласование.
- После реализации запусти доступные проверки, покажи отчёт и остановись.
- **Не переходи к следующему этапу автоматически.**
- Меняй статус задачи/этапа на «Завершён» в `PLAN.md` только после проверки результата и подтверждения пользователя.

## 4. Стек

Используй React, JavaScript (без TypeScript), Vite, Redux Toolkit, React Redux, **RTK Query**, `fetchBaseQuery`, React Router, Bootstrap 5 и собственный CSS.

- Для обычных запросов к Favorit Parts API используй RTK Query, **не `createAsyncThunk`**.
- **Не используй Axios**, если отдельного разрешения нет.
- Не добавляй другие стейт-менеджеры, CSS-фреймворки, отдельный backend, proxy или БД без согласования.
- Функциональные компоненты и React-хуки предпочтительны.

## 5. Архитектура и код

- Используй `createBrowserRouter` с объектами конфигурации маршрутов в `src/app/router.js` и `RouterProvider` в `main.jsx`; не используй `BrowserRouter` и JSX `Routes`/`Route`.
- Header закрепляй через Bootstrap `sticky-top` (position: sticky; top: 0), сохраняя его в потоке. Не добавляй компенсационные отступы под Header или раскрытое меню. Для маршрутов используется ScrollRestoration React Router.
- `App.jsx` — общий layout: отдельный компонент `Header` и `Outlet` для вложенных страниц. Header использует `Link`/`NavLink` для переходов без перезагрузки.
- Минимальный Header разрешён отдельной архитектурной задачей; фиксация, мобильное меню и оформление остаются этапом 3 и не выполняются автоматически.
- UI-компоненты отображают данные и обрабатывают взаимодействия; не делают прямых `fetch` вызовов.
- Серверные данные, кеш, загрузка и ошибки живут в RTK Query, а не дублируются в отдельных Redux slices.
- `searchSlice` предназначен для клиентского состояния поиска.
- Нормализация API и форматирование вынесены в утилиты/сервисный слой.
- Пиши простой код с понятными именами, избегай лишних абстракций и дублирования.
- Не меняй соседние, не относящиеся к задаче части проекта без необходимости.

## 6. API Favorit Parts

Основной endpoint: `GET http://api.favorit-parts.ru/hs/hsprice/`.

- Поиск по артикулу: `key`, `number`.
- Цены и аналоги: `key`, `number`, `brand`, `analogues=on`, `info=on`.
- Цена — из `warehouses[].price`, **не** `goods[].price`.
- Остаток — из `warehouses[].stock`.
- Дата отгрузки — `warehouses[].shipmentDate`.
- Учитывай ответы с `error`, пустую структуру вместо отсутствующего товара, нулевые остатки, пустые массивы аналогов/складов и необязательные поля.
- Кодируй все query-параметры корректно. Не выдумывай полей API.
- Не делай рабочий UI на фальшивых данных: временные mock-данные возможны только в явно выделенных тестах или демонстрациях.

## 7. Ключ, безопасность и ограничения браузера

- Храни локальные значения в `.env.local`; файл должен быть в `.gitignore`.
- **Не коммить ключи и не выводи их в отчёты/логи.**
- Переменные `VITE_*` видимы в браузере и **не сохраняют ключ в секрете**. Не представляй это как безопасную схему. Нужен ключ, разрешённый для тестового клиентского использования.
- Проект намеренно **без backend и proxy**.
- Ответ API при открытии адреса в браузере не доказывает работоспособность CORS; проверь реальный запрос со страницы приложения.
- При CORS, mixed content или другой блокировке остановись, объясни проблему, предложи варианты и запроси решение. Не отключай защиту браузера и не добавляй proxy самостоятельно.

## 8. UI и рамки MVP

- Оформление Header: фон #F3F3F3, нижняя линия 2px #E92327, ссылки #252525; hover и active — #E92327 с подчёркиванием, переходы 0.2s. На 768–991px кнопка «Посмотреть цены» не переносится и не создаёт горизонтальную прокрутку.
- Общий закреплённый Header (`position: sticky; top: 0`): YURAL FAVORIT, «Главная», «О нас», «Контакты».
- Главная: затемнённый фоновый **Ford Mustang**, поиск по центру первого экрана; ниже вертикальный список строк: производитель, артикул, название и кнопка «Посмотреть цены» в четырёх колонках с общей шапкой на Desktop и Tablet (от 768 px). На Phone производитель и артикул сверху, наименование ниже, кнопка внизу на всю ширину; горизонтальной прокрутки нет. При отсутствии реальных товаров показывается только «По вашему запросу ничего не найдено», без списка и его заголовков.
- Страница деталей: сначала таблица предложений выбранного производителя, ниже таблица аналогов; одна строка на складское предложение.
- Кнопка возврата должна сохранять текущий поиск и результаты при обычной навигации без повторного запроса.
- Используй светлую палитру, красные акценты, графитовый текст, Bootstrap и CSS; дизайн должен быть адаптивным.
- `docs/reference.jpg` используется только для палитры и общего визуального стиля. Для Hero на этапе 4 выбрано изображение `page/public/image/hero-mustang.png` (Ford Mustang); Vite publicDir — page/public, URL изображения — /image/hero-mustang.png; не копируй функциональность магазина с референса.
- **Не добавляй** корзину, аккаунты, регистрацию, каталог, платежи, историю поиска, сортировку и фильтры.
- На этапе 1 страницы «О нас» и «Контакты» имеют только минимальные заглушки; временное содержимое реализуется на этапе 3.

Перед тем как считать задачу готовой:

2. Запустить доступные тесты/линтер/сборку, если такие команды существуют.

5. Сообщить статус, изменённые файлы, результаты проверок, проблемы и предлагаемый следующий шаг.

После отчёта **остановись и жди согласования**.
