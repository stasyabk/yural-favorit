# YURAL FAVORIT — архитектура

**Версия:** 1.2

**Статус:** согласованная архитектура для MVP  
**Связанный документ:** `docs/PROJECT.md`

## 1. Подход

Клиентское SPA на React. В браузере три логических слоя:

1. **UI** — страницы и переиспользуемые компоненты.
2. **State** — локальное состояние в React/Redux Toolkit; серверные данные и кеш в RTK Query.
3. **API** — один RTK Query API slice с `fetchBaseQuery` для Favorit Parts.

```text
React pages/components
        | \
        |  \--> searchSlice (текущий поисковый артикул)
        v
RTK Query hooks --> favoritApi (fetchBaseQuery)
                           |
                           v
                  Favorit Parts HTTP API
```

Собственный сервер или proxy не используется. Это решение намеренное для локального теста и зависит от работоспособности CORS.

## 2. Стек

React, JavaScript, Vite, React Router, Redux Toolkit, React Redux, RTK Query, Bootstrap 5, CSS. **Не использовать TypeScript, Axios и `createAsyncThunk` для типовых запросов к API.**

## 4. Маршруты

| Маршрут | Страница |
| --- | --- |
| `/` | HomePage |
| `/parts/:brand/:number` | PartDetailsPage |
| `/about` | AboutPage |
| `/contacts` | ContactsPage |

Маршрутизация использует `createBrowserRouter`: единственный экземпляр роутера создаётся в `src/app/router.js` вне React-компонентов. Маршруты описываются объектами конфигурации с `path`, `Component` и `children`; главная страница — индексный дочерний маршрут. `main.jsx` подключает `RouterProvider` внутри Redux `Provider`. `BrowserRouter` и JSX `Routes`/`Route` не используются.

`App.jsx` — общий layout родительского маршрута `/`: отдельный `Header` из `src/components/Header/Header.jsx`, затем `main` с `Outlet` для дочерней страницы. Header сохраняется при переходах и использует `Link`/`NavLink`, чтобы не перезагружать документ. Все четыре URL из таблицы сохраняются и поддерживают прямое открытие.

Минимальный Header первоначально добавлен по отдельному разрешению на архитектурные изменения. На этапе 3 он закреплён сверху, получил текстовый логотип и адаптивную навигацию; информационные страницы получили временные тексты. Этап 3 завершён и принят пользователем. Окончательная стилизация MVP остаётся этапом 7.

Состояние мобильного меню хранится локально в `App`, а `Header` получает состояние и обработчики через props. До ширины 768 px навигация раскрывается кнопкой с `aria-expanded` и `aria-controls`; выбор ссылки закрывает меню, Escape закрывает его с возвратом фокуса на кнопку. Header использует Bootstrap `sticky-top` (`position: sticky; top: 0`) и остаётся в потоке документа, поэтому его фактическая высота, включая открытое меню, автоматически сдвигает содержимое `Outlet`. Компенсационных отступов и переменной `--mobile-menu-height` нет. `--header-height` задаёт высоту строки логотипа и используется для высоты первого экрана и scroll-margin, а не для компенсации Header. `RouteScrollManager` в App использует useLocation и submittedQuery из Redux и является единственным владельцем прокрутки маршрутов. Он устанавливает history.scrollRestoration = manual на время работы приложения; ScrollRestoration не подключается. Любая деталь, включая возврат из аналога, открывается с scrollY = 0. Главная с непустым submittedQuery в Redux позиционируется как после поиска; без него — сверху. Менеджер отслеживает location.key: изменения searchSlice в той же записи истории не запускают позиционирование, ответ ручного поиска обрабатывает HomePage.

`brand` и `number` в URL кодируются и декодируются корректно. Страница детали должна получать данные из API даже при открытии по прямой ссылке после реализации её интерфейса на этапе 5.

## 5. Redux и RTK Query

### searchSlice

Хранит **параметры интерфейса**, а не копии серверных данных. Минимальная модель:

```js
{
  query: "",          // значение текущего поиска
  submittedQuery: ""  // артикул, по которому показаны результаты
}
```

`query` может изменяться при вводе; `submittedQuery` обновляется после подтверждения поиска. Это исключает случайные запросы на каждое нажатие клавиши.

На этапе 6 searchSlice — единственный источник клиентских query/submittedQuery. setQuery меняет только ввод; submitSearch подтверждает непустой артикул с trim и заменяет предыдущие параметры. Серверных данных, статусов запросов и истории нескольких поисков в slice нет. HomePage хранит локально только сообщение валидации и ref одноразовой плавной прокрутки. Параметры больше не копируются в location.state, отдельной восстановительной подписки нет.

### favoritApi

Создать один `createApi` с `fetchBaseQuery` и двумя query-endpoints:

```text
getPartsByNumber(number)
getPartDetails({ number, brand })
```

Единственный useLazyGetPartsByNumberQuery поиска размещён в общем App и передаёт trigger/result в HomePage через Outlet context. Submit вызывает lazy trigger; RTK Query управляет кешем, статусами загрузки и ошибками. Store регистрирует searchReducer, reducer и middleware favoritApi. Другие страницы не создают поисковые подписки.

Параметры:

- `getPartsByNumber`: `key`, `number`.
- `getPartDetails`: `key`, `number`, `brand`, `analogues=on`, `info=on`.

В RTK Query `fetchBaseQuery` использует `params`, чтобы корректно кодировать номер и производителя. Если ответ содержит поле `error` при HTTP 200, нормализовать его в ошибку RTK Query (например, через `transformResponse`/кастомный `baseQuery`-wrapper), не показывать как успешный результат.

### Возврат к поиску без запроса

RTK Query — источник серверных данных. При переходе со страницы результатов детали поиск может стать неиспользуемым кешем, который удаляется по истечении `keepUnusedDataFor`.

Активная lazy-подписка удерживается в App на всё время текущей сессии, включая просмотр детали, аналога и информационных страниц. Поэтому для последнего подтверждённого поиска таймер удаления неиспользуемого кеша не запускается: произвольного увеличения keepUnusedDataFor нет. HomePage при возвращении читает тот же result из Outlet context и не вызывает trigger, поэтому повторного поискового запроса нет. Новый submit меняет параметры Redux и вызывает trigger заново; предыдущая подписка освобождается, прежний кеш удаляется по стандартному keepUnusedDataFor (60 секунд в установленной версии). Удерживается только текущий результат, интерфейс истории не создаётся. currentData и isFetching скрывают устаревшие строки при новом запросе; завершение старого запроса не подменяет текущую выдачу.

При полной перезагрузке страницы гарантированно сохранять результаты не требуется. Постоянная история поиска не создаётся.

## 6. Работа с данными

Схема ответа описана в `docs/PROJECT.md` и исходном `wsprice.pdf`.

### Строки результатов поиска

`goods` → элементы списка с `brand`, `number`, `name` (при необходимости `goodsID` как вспомогательный идентификатор). Нормализация допускает только записи с непустыми brand и number: технический goodsID или возвращённый артикул без производителя не создают результат. Отсутствие необязательного name или нулевой stock не исключают реальный товар. При пустом нормализованном массиве HomePage скрывает список, шапку и счётчик, показывая только «По вашему запросу ничего не найдено».

### Страница детали

`goods` выбранного производителя → раскрыть массивы `warehouses` в плоские строки предложений. Вложенные `analogues` → уникальный список объектов { brand, number, name } по точной паре brand + number. Ключ Map — JSON-представление пары, без изменения регистра или значения. Порядок первого появления сохраняется; первое последующее непустое имя заполняет отсутствующее. Аналоги без складов не исключаются. Поля price, stock и warehouses в нормализованном списке отсутствуют.

Каждая строка первой таблицы должна сохранять:

- `brand`, `number`, `name` исходной детали;
- склад `code` (если непустой) либо `id`;
- `price` только из объекта склада;
- `stock` только из объекта склада;
- `shipmentDate` при наличии.

Складские предложения первой таблицы не удаляются и не объединяются. Для выбранной детали без складов показывается пустое состояние первой таблицы. Для списка аналогов пользователь согласовал объединение по brand + number; склады этих аналогов загружаются при переходе на существующий маршрут /parts/:brand/:number. PartsTable и преобразование первой таблицы не меняются.

Дата `shipmentDate` содержит дату отгрузки и время предельного оформления заказа; отображение должно не вводить в заблуждение и не создавать вымышленных сроков. По согласованию пользователя на этапе 5 цены отображаются числом без обозначения валюты; текст «Цены указаны без обозначения валюты» в UI удалён. `utils/formatters.js` форматирует число по ru-RU без добавления символа валюты, сохраняет нулевые значения и возвращает «—» для отсутствующей/некорректной цены. Дата отгрузки выводится исходной строкой API, включая время и часовой пояс; автоматический перевод времени не выполняется. Учитывать позиции с нулевыми остатками и признаки `notRefund`, хотя отображение отдельного бейджа для них в MVP не запланировано.

Нормализацию и форматирование вынести в `utils` и покрыть тестами на типовые/пустые ответы.

## 7. Работа с ключом, HTTP и CORS

API: `http://api.favorit-parts.ru/hs/hsprice/`.

Локальные переменные (пример без реального ключа):

```dotenv
VITE_FAVORIT_API_URL=http://api.favorit-parts.ru/hs/hsprice/
VITE_FAVORIT_API_KEY=
```

`.env.local` должен игнорироваться Git. **Важное ограничение:** значения `VITE_*` встраиваются в клиентский JS, и ключ виден в браузере/запросах; это не безопасное хранилище. Для теста применять только подходящий ключ, который разрешено использовать таким образом.

Получение JSON-ответа при открытии URL в адресной строке не проверяет CORS. Первой интеграционной проверкой должен быть настоящий `fetch`/RTK Query запрос из работающего приложения на другом origin. HTTP API недоступен с HTTPS-страницы из-за mixed content; для локального теста учесть протокол страницы.

При CORS/mixed-content/сетевой блокировке — сообщить пользователю и остановиться; не добавлять proxy, backend и не отключать защиту браузера без согласования.

Проверка из Edge 27.10.2026 со страницы `http://localhost:5173/`: оба запроса вернули HTTP 200 и `Access-Control-Allow-Origin: *`. В исходных JSON присутствует заполненный массив `goods`, поле `error` отсутствует. Для артикула `0986424794` зафиксированы 1 товар с производителем, артикулом и наименованием, 17 складских предложений и 408 вложенных аналогов в ответе деталей (2992 складские строки аналогов после нормализации). Это реальные ответы API; данные в процессе проверки не подменялись. Ключ и URL с ключом в отчёт не включаются.

## 8. Компоненты и страницы

- `Header`: адаптивная навигация с `position: sticky; top: 0` (Bootstrap `sticky-top`).
- `SearchBar`: управляемый ввод и отправка подтверждённого артикула.
- `PartCard`: строка `tr` с четырьмя ячейками (производитель, артикул, наименование, действие) внутри таблицы результатов HomePage; имя компонента сохранено.
- `PartsTable`: семантическая таблица из семи колонок для складских предложений выбранного производителя. Пустой массив показывает сообщение раздела вместо фиктивной строки; таблица на узких экранах горизонтально прокручивается в собственном контейнере Bootstrap table-responsive. offers-scroll имеет height: auto, max-height: none, overflow-x: auto и overflow-y: hidden: все складские строки определяют высоту контейнера, внутренней вертикальной прокрутки нет. Стили находятся в styles/details.css.
- `Loader` / `ErrorMessage`: общие индикаторы и сообщения.
- `HomePage`: hero с Ford Mustang, форма, список результатов.
- `AnaloguesTable`: четыре колонки (brand, number, name, «Посмотреть наличие»), без складских данных. Ссылки кодируют параметры и открывают тот же маршрут детали; изменение useParams запускает getPartDetails с новыми аргументами, currentData исключает показ предыдущей детали. На Phone строки перестраиваются вертикально, на Tablet/Desktop остаются горизонтальными; горизонтальной прокрутки списка нет. На 768–991px колонка действия расширена до 210px для подписи кнопки.
- `PartDetailsPage`: параметры brand/number из useParams, getPartDetails через RTK Query, заголовок, две таблицы и кнопку «Назад». При history.state.idx > 0 выполняется navigate(-1); при отсутствии внутренней истории — navigate на / с replace. Внешняя история браузера не определяется через history.length. Для исключения устаревших данных используется currentData; состояния загрузки и ошибки показываются отдельно от таблиц. Клиентские параметры сохраняются в searchSlice, активный поисковый result удерживается подпиской App; возврат не обращается к поисковому endpoint.
- `AboutPage` и `ContactsPage`: временные тексты.

## 10. Проверки архитектуры

- API-запросы сосредоточены в RTK Query, а не разбросаны по компонентам.
- Нет дублирования массива товаров из RTK Query в обычных Redux slices без причины.
- URL детали поддерживает прямое открытие.
- Поиск сохраняется при обычной навигации назад.
- Ошибки API и пустые структуры обрабатываются отдельно от успешных результатов.
- Нет тайно добавленных proxy/backend или нового функционала.

Vite использует стандартный publicDir (корневая папка `public`); явная настройка publicDir удалена. Исходный Mustang хранится в `public/images/hero-mustang.png`, доступен по URL `/images/hero-mustang.png` и копируется без изменений в `dist/images/hero-mustang.png`. URL одинаков в dev и production preview; пустые каталоги page/public/image, page/public и page удалены.

HomePage запускает плавную прокрутку только после завершения ручного submit. Общая утилита utils/scroll.js вычисляет targetY = scrollY + Hero.getBoundingClientRect().bottom − фактическая высота Header + 10. Получается Header.bottom − Hero.bottom = 10px в координатах viewport, а заголовок результатов остаётся ниже Header. Область search-results имеет min-height: calc(100dvh − var(--header-height) + 10px), чтобы точная позиция была достижима и при короткой/пустой выдаче. RouteScrollManager вызывает ту же утилиту с behavior: instant при возврате к главной с submittedQuery из Redux; остальные страницы открывает сверху. HomePage не запускает повторную плавную прокрутку при восстановлении кеша. Запланированные requestAnimationFrame отменяются при смене маршрута; параллельного восстановления браузером или ScrollRestoration нет.
